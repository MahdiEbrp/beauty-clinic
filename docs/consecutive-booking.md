# Consecutive public booking slots

The public wizard chooses one **start** for an ordered run of services. Each
service unit consumes one seat in its own slot; quantities are expanded into
unit reservations. The next unit starts exactly at the preceding slot's end
on the same date. Slot durations come from existing records, not a hardcoded
15-minute assumption. Every eligible start is offered (a sliding window, not
disjoint chunks). No new slots are generated by the availability endpoints.

## Availability and client state

- `/api/public/slots?date=…&items=…` accepts bounded JSON containing ordered
  `{groupId, quantity}` requests and returns starts with per-unit assignments.
- `/api/public/availability-days?from=…&to=…&items=…` uses the same planner, so
  a date is offered only when a whole run can fit.
- Every assigned slot must be active, in the future, have a free seat, and
  accept its assigned service group. Gaps, full slots and day boundaries stop
  the run. Capacity is **not** compared with the order's total service count.
- Cache keys include group order and individual quantities. Cart lines retain
  per-unit IDs plus their first-to-last display range. The wizard rejects old
  shared-slot carts; users must select a new start after upgrading.
- The old single-group/shared-capacity read query formats remain available to
  older integrations; the wizard now uses ordered `items` queries instead.

## Creation and compatibility

Both public creation routes enforce consecutive mode, irrespective of the
client flag. The payload contains one item with quantity 1 for every selected
slot (up to 100). Repeated slots, gaps, changed times and cross-day sequences
are rejected. Staff/internal calls without consecutive mode retain the old
explicit capacity-based allocation behavior.

Inside one transaction, all referenced slots are locked in global ID order.
Counts, group links and customer conflicts are batch-loaded using the same
transaction connection; all validation precedes one bulk insert. Adjacent
appointments use half-open intervals, so touching boundaries are not conflicts.
The fixed deposit is recorded on only the first row of the order as before.

No database migration or seed is needed. Deploy the frontend and API together.
Tests use mocked database transactions and jsdom; a live PostgreSQL contention
and end-to-end checkout check remains advisable before production rollout.
